# CT-01 — Expert: Professional Workflow, Versioning and Client Revisions

**Course:** Video Editing  
**Pathway stage:** Expert

## Learning outcomes
Translate a client brief into an edit plan; manage versions and feedback; maintain traceability; distinguish subjective notes from technical defects; prepare reliable review exports.

## Prerequisites
Lessons 01–10 and a completed rough cut.

## Key definitions
- Brief: written description of audience, purpose, message, deliverables and constraints.
- Scope: agreed work and deliverables.
- Revision round: defined cycle of client feedback and editor changes.
- Version control: systematic naming and tracking of project states.
- Review export: low-risk file supplied for feedback, clearly marked with version and status.
- Picture lock: approved state where editorial picture changes are restricted, except agreed corrections.
- Change request: request that alters approved scope or requirements.
- Timecoded note: feedback tied to a specific time in the video.
- Conform: rebuilding or matching the final sequence against approved editorial decisions or source media.

## Why it matters
Professional editing includes communication, accountability and predictable handoff. Without clear versions, feedback can be applied to the wrong cut and approved work can be overwritten.

## Theory
A useful brief records purpose, audience, key message, deliverables, aspect ratios, duration, platform, language, captions, rights, deadline, approval owner and technical requirements. Distinguish required changes from preferences. Consolidate feedback through one authorized decision-maker where possible.

Use version names that communicate project, date, version and status. Do not label an unapproved draft “final.” Preserve prior approved versions and maintain a change log. A review export should identify itself clearly and should not accidentally be published as a master.

## Tools and alternatives
Versioned project copies, source control for text/configuration where appropriate, review platforms with timecoded comments, spreadsheets and a change log. Do not place large binary media in a source-control system unless the workflow is designed for it.

## Procedure
1. Convert the brief into a deliverables checklist and acceptance criteria.
2. Confirm who can approve changes and how feedback will be delivered.
3. Establish project naming and version numbering before the first review.
4. Create a baseline project copy and record its location.
5. Export a review file with clear draft status and version label.
6. Collect feedback and normalize notes into timecode, requested change, rationale, priority and owner.
7. Identify conflicts or ambiguous notes and request clarification before editing.
8. Apply changes to a new version, never overwrite the approved baseline.
9. Compare the revised export against the previous version and acceptance criteria.
10. Record completed, rejected and deferred notes with reasons.
11. Obtain approval for picture lock and record its scope.
12. Package the project and prepare a change summary.

## Worked example
Client note: “Make the opening faster.” Convert this into a specific review question: which section feels slow, and should the editor shorten the establishing shot, remove a pause or change the opening order? Record the chosen action and the resulting version number.

## Dry run
Create V01 rough cut, V02 with three timecoded changes and V03 approved picture lock. Make a table listing note ID, timecode, request, status and version implemented. Confirm each note is traceable.

## Guided exercise
Take five sample feedback notes, classify each as creative preference, factual correction, technical defect or scope change. Resolve contradictions and prepare a revision plan.

## Independent assignment
Submit a client-ready review package: brief, version log, timecoded feedback sheet, V01/V02 comparison, approval record and change summary.

## Common errors and recovery
- Editing the wrong version: stop, compare file timestamps and version logs, then apply changes to the correct baseline.
- Contradictory notes: escalate to the authorized approver.
- Scope expands silently: document the change request and agree impact before proceeding.
- “Final” used too early: label draft/review/approved/master states explicitly.
- Notes lack timecodes: request timecoded references or add them during review.
- Old review link remains active: mark superseded versions clearly and direct reviewers to the current one.

## Knowledge check
1. What information belongs in a useful brief?
2. Why create a new version for revisions?
3. What is picture lock?
4. How should conflicting feedback be handled?
5. What distinguishes a scope change from a normal revision?

## Answer key
1. Audience, purpose, deliverables, platform, duration, formats, language, rights, deadline and approval path.
2. To preserve history and prevent overwriting approved work.
3. An approved editorial state with picture changes restricted by agreement.
4. Ask the authorized approver to resolve the conflict before editing.
5. It changes agreed deliverables or requirements rather than refining the existing scope.

## Assessment rubric — 30 points
Brief/acceptance criteria 6; version traceability 8; feedback interpretation 6; revision validation 6; approval/handoff records 4. Pass 24/30.

## Quality-control checklist
- [ ] Current version is clearly identified.
- [ ] Feedback notes have timecodes and owners.
- [ ] Prior versions are preserved.
- [ ] Scope changes are documented.
- [ ] Review export is labeled draft/review.
- [ ] Approval and picture-lock state recorded.

## Further study
Study production contracts, change control, review-platform security, client communication and post-production scheduling.
