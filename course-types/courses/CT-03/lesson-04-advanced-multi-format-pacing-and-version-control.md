# CT-03 Lesson 04 — Advanced Multi-Format Pacing and Version Control

- Course: CT-03 — Short-Form & Social Video Editing
- Level: Advanced
- Estimated time: 150 minutes
- Prerequisites: Lessons 01–03; one approved short-form edit and its source project
- Tools/environment: Any editor with sequence duplication, transforms, markers and export presets; record app/version and OS
- Version/review date: Tool-neutral curriculum; verify destination platform requirements before delivery

## Learning outcomes
Learners can:
- design a multi-format edit system from one approved source;
- distinguish a master edit from platform adaptations;
- maintain pacing and narrative clarity across different runtimes;
- manage versions, change requests and exports without overwriting approved work.

## Key definitions
| Term | Definition | Context |
|---|---|---|
| Master edit | Approved editorial source from which adaptations are made | Protects a canonical version |
| Adaptation | A version recomposed for a different audience, aspect ratio or runtime | 9:16, 1:1 and 16:9 |
| Version control | Naming and recording changes so a file's identity and history are clear | v01, v02, approved |
| Change log | Record of requested, accepted and implemented changes | Client revision tracking |
| Modular timeline | Timeline organized into meaningful sections or nested sequences | Opening, proof, CTA |
| Platform-safe composition | Composition designed to avoid edge/UI obstruction | Important text stays clear |

## Purpose and theory
One campaign may require multiple aspect ratios, durations, languages and calls to action. A professional workflow does not export the same timeline blindly into every format. Each adaptation has its own composition, timing and acceptance criteria. The approved master is preserved; derivative versions are traceable.

Pacing is the relationship between shot duration, action, information and viewer comprehension. A faster cut rate is not automatically better. A technical demonstration may require time to inspect; a reaction may require a pause; a CTA must remain visible long enough to understand.

## Tools and alternatives
Use a timeline editor that supports duplicate sequences or project versions. A spreadsheet, plain-text change log or issue tracker can manage requests. For small projects, folders and consistent filenames may be enough; for team projects, use a shared version-control or asset-management system with permissions and backups.

## Procedure
1. Freeze the approved master and record its filename, date, duration and specification.
2. Create derivative sequences; never overwrite the master.
3. Map the central message and required evidence for every target format.
4. Create a shot-by-shot adaptation plan noting crop, reposition, text changes and alternate footage.
5. Review pacing against the target runtime and information density.
6. Preserve necessary pauses, demonstrations, qualifiers and CTA reading time.
7. Create a change log with request ID, requester, exact change, affected versions, status and approval.
8. Use filenames that encode project, platform, ratio, language, version and date.
9. Keep draft, review and approved states distinct.
10. Export a short proof before rendering the full set.
11. Compare each export to its own specification and watch it completely.
12. Archive the project, linked assets, master and derivative manifest.

## Worked example
A 45-second product demonstration must become a 30-second vertical feed edit and a 15-second story edit. The 30-second version preserves problem, feature proof and CTA. The 15-second version uses one strongest demonstration and a concise CTA; it does not imply that omitted features were shown. Captions are resized and repositioned for each composition rather than scaled mechanically.

## Dry run
A client requests: “Make the opening faster and change the price.” Convert this into two separate change items. Ask which approved price and effective date are authoritative before changing a factual claim. For the opening, propose a specific timecode range and a measurable result such as removing a redundant setup shot. Save a new version and compare it against the approved reference.

## Guided practice
Create two derivatives from one 20–30 second master. Record all composition changes and create a version manifest. Ask a reviewer to identify which file is the approved master without opening the project.

## Independent assignment
Deliver three formats from one brief, a change log, a version manifest and a comparison note describing editorial differences. Include one rejected change and explain why it would reduce clarity or factual accuracy.

## Common errors and recovery
| Symptom | Likely cause | Diagnosis | Recovery |
|---|---|---|---|
| Master overwritten | Derivatives created in same sequence | Inspect project history/backups | Restore approved copy and branch derivatives |
| CTA too brief | Runtime reduced without reading-time review | Watch at normal speed | Simplify copy or reallocate time |
| Crop hides product | Blind preset application | Inspect each shot | Reframe individually or choose alternate shot |
| Wrong price in one export | Untracked change | Compare manifest and overlays | Correct all affected versions and retest |
| File ambiguity | Weak naming/version convention | Inspect delivery folder | Rename consistently and update manifest |

## Knowledge check
1. Why preserve a master edit?
2. What makes an adaptation different from a resized export?
3. What information belongs in a change log?
4. Why does faster cutting not always improve pacing?
5. How should a factual change such as price be verified?

## Answer guidance
1. It protects the approved editorial source and makes derivatives traceable.
2. It may require new framing, timing, graphics, language and story decisions.
3. Request, owner, exact change, affected version, approval and status.
4. Viewers need time to understand action, evidence and text.
5. Confirm an authoritative current source and approval before updating.

## Assessment rubric — 25 points
Master preservation 4; adaptation decisions 6; pacing and message clarity 5; version/change log 5; export validation 5. Pass: 20/25; factual accuracy and source preservation are mandatory.

## QC checklist
- [ ] Master preserved and identified.
- [ ] Each adaptation has a distinct specification.
- [ ] Reframing is checked shot by shot.
- [ ] Factual overlays are verified.
- [ ] Change log and filenames agree.
- [ ] Each export was watched completely.
- [ ] Handoff contains editable project and manifest.
